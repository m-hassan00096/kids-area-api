# Kids Area — Backend Code Standards

> **Status:** Approved coding conventions for V1; implementation not started.  
> **Location:** `docs/02-standards/code-standards.md`  
> **Scope:** Laravel 12 backend only; one Kids Area location, one MySQL 8 database, API-first hybrid modular monolith.  
> **Related documents:** [Project Overview](../00-overview/project-overview.md), [Backend Architecture](../01-architecture/backend-architecture.md), the relevant standards in this directory, and the active Spec Kit feature specification.

## 1. Purpose & Principles

This document specifies **how PHP code is organized and written** across Kids Area. It is a cross-module coding standard, **not** an inventory of feature requirements, database tables, permissions, or HTTP endpoints.

1. **Follow Laravel conventions first.** Prefer native framework facilities over homegrown frameworks or generic abstraction layers.
2. **Preserve module ownership.** Each business module owns its records, business invariants, and write operations.
3. **Keep controllers thin.** Controllers own the HTTP boundary; they do not perform writes or coordinate business workflows.
4. **Make every mutation explicit.** All creates, updates, deletes, state transitions, payments, and other writes go through a focused **Action**, including simple CRUD.
5. **Use Services deliberately.** Extract reusable calculations or substantial shared behavior, not one service per model by habit.
6. **Keep critical work synchronous.** V1 must work on shared hosting/cPanel **without queues, queued jobs, Redis, cron, scheduler-dependent flows, or application workers**.
7. **Protect financial and timer integrity.** Use exact arithmetic, transactions, necessary row locks, uniqueness, idempotency, and preserving history.
8. **Test and format changes before merging.** PHPUnit and Laravel Pint checks are mandatory for PRs to `develop`.
9. **Do not duplicate specifications.** The API, database, errors, authorization, and localization details belong to their own standards or feature specs.

### Placement rules

- **Module-local:** domain models, migrations, request classes, actions, reusable business services, policies, resources, feature-specific exceptions and fixed-status enums.
- **Application core:** small shared response/error infrastructure, common middleware, localization configuration, centralized Select Registry, and selective Audit Logger.
- **Select providers:** each owning business module supplies its **read-only**, permission-aware selection logic. Do not create a standalone Selects business module.
- **User vs Employee:** Identity owns system user accounts and access decisions; Employees owns staff profiles/contracts. Their association is optional; never collapse them into one entity.
- **No universal hierarchy:** do not create compulsory `Domain/Application/Infrastructure` trees, repositories, BaseControllers, generic Managers, or DTOs for every model.

## 4. Class Responsibilities & Read/Write Conventions

| Component | Responsibility | Must avoid |
|---|---|---|
| **Controller** | Receive request, delegate mutations to Actions; perform **simple authorized reads**; return shared API responses/Resources | Direct `create/update/save/delete`; monetary calculations; timer transitions; workflow orchestration |
| **Form Request** | Validate and normalize external input; enforce simple request-level authorization when appropriate | Database-dependent business decisions under concurrency; posting money |
| **Action** | Own **one write use case**, enforce current-state business invariants, coordinate needed transactions, call owning modules' public operations | Returning raw HTTP responses; unrelated responsibilities; unguarded cross-module writes |
| **Service / Calculator** | Substantial, reusable business logic or complex calculations used by Actions or approved reads | One-to-one CRUD mirrors of Actions; hidden persistence unless it is an explicitly owned operation |
| **Model** | Eloquent relationships, casts, local scopes, simple record-level behavior | Orchestrating cross-module changes; hidden billing/posting side effects |
| **Policy / Gate** | Enforce actor's permission for a capability or **this record** | Replacing the Action's current-state business checks |
| **Resource** | Explicitly serialize allowed data fields/relationships and public labels | Database mutations or hidden recalculation of authoritative totals |
| **Query Class** | Nontrivial or repeated read-only queries that merit extraction | Abstracting every simple `index` or `show` query without benefit |
| **Select Provider** | Authorized small/bounded dropdown options for its owning module | Exposing unbounded tables or bypassing read permissions |

### Mutation pattern — required

**Every write goes through an Action**, including simple CRUD. Prefer a focused, clearly named class with a single public `execute(...)` entry point. A one-row CRUD Action may be only a few lines; do not add a matching Service, Repository, DTO, or Contract without need.

```php
// Illustrative; imports, namespace and fields follow the installed module.
final class UpdateCafeProductAction
{
    public function execute(CafeProduct $product, array $validated): CafeProduct
    {
        $product->update($validated);

        return $product->refresh();
    }
}
```

A controller receives a Form Request, calls the Action via dependency injection, and returns an API Resource using the project's approved response helper. Do not pass `$request->all()` into unrestricted model mass assignment.

### Read pattern — approved exception to HTTP-only controllers

- A **simple read-only** `index` or `show` query may remain inside the Controller, using Eloquent or Laravel Query Builder, after authorization and any needed scoping.
- Extract **complex, repeated, aggregate, sensitive**, or cross-module reads into an owning module's Query Class or read Service when doing so improves clarity/testability.
- Query placement never overrides permissions, filtering, pagination, or explicit Resource output.
- Read operations must **not mutate data** or create business side effects.

**Clarification:** “Controllers are HTTP-only” means **no writes and no business workflows**; it does not forbid straightforward authorized read queries.

## 5. Cross-Module Collaboration & Shared Select Registry

Kids Area is a **hybrid** modular monolith: the modules live inside one Laravel process and share one MySQL database, but business ownership remains explicit.

- **Cross-module reads:** an ordinary, authorized read or Eloquent relationship is acceptable when it does not bypass another module's sensitive read rules.
- **Cross-module writes:** call the **owning module's Action or approved Service/Contract**, instead of mutating that module's tables directly.
- **Contracts/interfaces:** introduce them when they protect a meaningful changing dependency or simplify integration tests—not merely to avoid in-process calls.
- **Atomic multi-module workflows:** one coordinating Action owns the outer `DB::transaction()`; downstream owning operations participate synchronously in the same transaction.
- **No HTTP between modules.** Do not create internal REST calls for code that runs in the same Laravel process.
- **Events:** optional synchronous, noncritical decoupling only if a concrete consumer exists. Money posting, timer transitions, refunds, and essential audit/financial writes must **not depend on delayed event processing**.

### Example: closing a session

```text
CloseSessionAction (Sessions; orchestration)
  -> verify/lock session, all timers finished, and final charges
  -> POS-owned operation creates exactly one invoice/payment
  -> Finance-owned operation posts the canonical financial movement
  -> mark the session closed and link its invoice
  -> commit the entire operation; otherwise roll everything back
```

The POS owns invoice/payment state; Finance owns posted financial movements. Reports is read-only for business facts and must not post the same receipt again.

### Central Select Registry

- A single, shared `GET /api/v1/selects?selects=...` endpoint aggregates **bounded option lists**, following the approved `printingApi` model.
- The **Core** application owns registry/dispatch; **individual modules** register their allowed keys/providers.
- Each provider owns its read query, eligibility constraints, Arabic labels and **per-key authorization**.
- Validate requested keys and allowed parameters. Reject unknown keys and unauthorized requests rather than silently exposing or skipping data.
- Return the already-agreed `data` **array of {label, options} objects**, with `options` containing `{value, label}`. Do not silently substitute the differently shaped reference sample that returns an object keyed by select names.
- Use normal paginated/search endpoints for large business lists. Don't send all children, guardians, customers, or transactions as unbounded dropdowns.
- The precise transport, error cases, and option value types are owned by `api-standards.md` and the relevant feature specs.

## 6. Naming, Types & Enums

| Element | Standard | Example |
|---|---|---|
| Classes / enum types | `PascalCase` | `CloseSessionAction`, `TimerStatus` |
| Methods / PHP variables | `camelCase` | `calculateCharge()`, `$activeSeconds` |
| Action names | Verb + domain noun + `Action` | `RefundInvoiceAction` |
| Query classes | Intent + `Query` when needed | `PayrollSummaryQuery` |
| Services/calculators | Meaningful capability name | `TimerCalculator` |
| Tables / columns | `snake_case` | `financial_movements`, `child_id` |
| Permission identifiers | Stable lowercase English dot notation | `sessions.close` |
| Translation keys | Stable English dot notation | `sessions.timer.invalid_transition` |
| API JSON/query field names | **Deferred to `api-standards.md`** | No accidental commitment here |

- Write descriptive full domain names; avoid ambiguous abbreviations.
- Use strict parameter and return types when practical; nullable and union types only when meaningful.
- Use constructor/method injection for application dependencies. Prefer immutable input where it matters, but do not mandate DTO classes for simple validated arrays.
- Do not use raw SQL, PHP floats, or loosely typed values to sidestep important financial constraints.
- Use explicit Eloquent casts and relationships; do not derive authoritative financial totals from translated display labels.

### Fixed statuses and enums — approved

- **Fixed business states use integer-backed PHP enums**. Persist stable numeric values and expose human-readable Arabic labels through the Resource/localization boundary as specified in API Standards.
- **Simple on/off flags** (e.g., `is_active`) are database booleans with normal casts.
- **User-managed catalogues** (e.g., job types or activity records) are relational tables, **not enums**.
- Enum case names should be expressive and stable, using `UPPER_SNAKE_CASE`; avoid scattering raw integers across Actions and Controllers.
- Once persisted, **never reassign an existing numeric enum value to a new meaning** without an explicit migration/data preservation plan.
- The **actual numeric values** for timer, session, subscription, payroll or financial statuses belong to their owning feature specifications.

```php
// Illustrative only: case values must be finalized in the Sessions spec.
enum TimerStatus: int
{
    case READY = 0;
    case RUNNING = 1;
    case PAUSED = 2;
    case FINISHED = 3;
}
```

## 7. Validation, Authorization & Business Rules

Use three explicit responsibilities, without pretending that a pre-request validation check prevents races.

1. **Form Requests** validate required fields, formats, simple relations and input structure. Normalize only what is safe to normalize.
2. **Policies/Gates/permission middleware** enforce authorization for the current user/record. Do not rely on a frontend button or a fixed role-name conditional such as `role == reception`.
3. **Actions** enforce current-state **business invariants at execution time**, inside the appropriate transaction/lock when another request could change the outcome.

Examples:

- `CreateSubscriptionAction` verifies the target group belongs to the selected activity, the child is eligible, and any configured capacity still has a free seat **at reservation time**, protected against concurrent last-seat enrollment.
- `PauseTimerAction` must reject an already paused, finished, or otherwise invalid timer transition using the current persisted state.
- `RefundInvoiceAction` validates permission, reason, refundable amount, existing refunds, and current invoice/payment state before writing a reversal/correction.
- `FinalizePayrollAction` verifies approved payroll figures and prevents the same payout being recorded twice.
- No Action trusts a client-provided total, remaining balance, eligible class count, elapsed time, price snapshot, or permission list as authoritative.

Expected business failures should throw focused business exceptions (or a shared business exception when enough); map them centrally to API errors per `error-handling-standards.md`. Controllers must not fill with repetitive `try/catch` or construct inconsistent error JSON.

## 8. Transactions, Concurrency, Money & Timer Integrity

**Use transactions when related records must succeed or fail as one business operation.** The coordinating Action defines the transaction boundary; simple one-record writes do not require a redundant explicit transaction by default.

| Operation | Required safety |
|---|---|
| Close session + settlement | One outer transaction; lock session; ensure timers finished; create one invoice, one full payment and matching financial movement |
| Create monthly subscription | Validate child/group, month and optional capacity under safe concurrent enrollment; retain exact price snapshot |
| Collect an installment | Payment and canonical financial movement commit together; no second subscription sale |
| Refund or invoice cancellation | Authorize, capture reason, verify refundable amount, append traceable correction; never erase original posted money |
| Record expense from a cashier shift | Update expected cash through the canonical movement; enforce open shift/permission |
| Payout salary | Prevent duplicate payout and preserve manager adjustments/audit |
| Start/pause/resume/finish timer | Lock/check current state; persist server timestamp, current state and relevant time-segment history together |
| Substitute trainer / delivered class | Preserve which trainer actually delivered the class; prevent duplicate per-class compensation |

### Mandatory safeguards

- `DB::transaction()` for atomic multi-record operations; short transaction durations.
- `lockForUpdate()` or equivalent serialization when concurrent requests can change an outcome; lock records in a consistent order to reduce deadlocks.
- Database **foreign keys, unique constraints and scoped idempotency identifiers** for critical retryable writes. A read-before-create check alone cannot guarantee uniqueness.
- Repeated identical financial commands must not create duplicate invoices, receipts, refunds, salary payouts or movements. A conflicting reuse must fail safely under the API error contract.
- **Exact monetary arithmetic** only; persisted money uses MySQL decimal columns. The exact column precision and arithmetic strategy are owned by Database Standards.
- **Financial Movements is the source of truth.** Derived balances/summary fields are nonauthoritative. Posted movements are corrected through **linked new entries**, not overwritten or deleted.
- Timer elapsed time is derived from **server timestamps and persisted segments**, not frontend intervals. Never update MySQL every second for a live timer.
- Record timestamps consistently in UTC; present local times according to the application/frontend formatting policy.
- Do not perform long exports, remote API calls, uploads, or other irreversible operations while holding financial row locks.
- Do not complete any critical business operation via a background Job, async listener, queue, or scheduler in V1.

**Explicitly deferred:** precise minute/second and money rounding rules; finalized enum values; idempotency key scope/retention; and detailed group booking/pricing edge cases belong in the relevant feature specs.

## 9. Queries, Filtering & Performance

- Keep common read queries readable. Extract a reusable or complex query only when the shape warrants it.
- Eager-load approved relations when needed and avoid N+1 requests.
- Paginate ordinary lists; never use unbounded `Model::all()` for operational tables, exports or large selects.
- Apply backend authorization and visibility rules **inside queries** for children, guardians, staff records, finances and reports.
- Use explicit allowed filters/sorts/includes. Whether a dedicated API query package is adopted and the public parameter syntax are specified in `api-standards.md`.
- Create measured, relevant indexes in module-owned migrations. Do not add an index/cache layer to everything by default.
- Prefer bounded, synchronous report generation with sensible size/time limits for cPanel. Never assume a background worker will finish an export.
- Add caching only with a measured reason, clear invalidation strategy, and no need for Redis or a continuous worker.

## 10. Testing, Pint & CI Quality

**PHPUnit is mandatory** for feature behavior, authorization and financial/state changes. Use focused Unit tests for deterministic calculations and Feature/Integration tests for API behavior, persistence and module collaboration.

| Change | Minimum verification |
|---|---|
| Read API | Authorized/denied access, response data/Resource shape, allowed filters and pagination |
| Action / mutation | Success, validation failure, missing permission, invalid current state, persisted side effects |
| Timer | Independent parallel timers, pause exclusion, reconnect/state recovery, invalid transitions, concurrent commands |
| Monthly subscription | Group capacity/concurrent enrollment, period validity, partial receipts, manual renewal, make-up grace window |
| POS / Finance | Full settlement, linked payment + movement, rollback, idempotency, partial/full refund limits, cashier cash reconciliation |
| Workforce / Payroll | Class attendance, delivered-class attribution, substitution, proposed vs approved deductions, duplicate payout prevention |
| Audit / Permissions | Sensitive-change actor/time/reason, authorized scope, no private data leakage |
| Shared selects | Registered keys, requested shape, option eligibility, per-key permissions, invalid/unknown key behavior |

- Use independent fixtures/factories; tests must not rely on execution order or production data.
- Run **MySQL 8** for tests where locks, foreign keys, transactions, uniqueness or concurrency matter. SQLite is **not evidence** of MySQL locking correctness.
- Add a regression test when fixing a business-rule or security bug.
- Use `vendor/bin/pint --test` as a **required, non-mutating CI formatting check**. Developers may run `vendor/bin/pint` locally to fix formatting.
- GitHub Actions must run relevant PHPUnit tests using MySQL 8 and Pint for PRs **targeting `develop`**. **Both must pass** before merge; enforce through a branch-protection/ruleset when configured.
- A green test report can only be claimed for checks **actually executed**. Do not treat an unconfigured workflow or an unexecuted test as passed.
- Static analysis tools may be evaluated later; **PHPStan/Rector or similar tools are not compulsory in V1** without a separate decision.

Sample local commands (once the Laravel project and dependencies actually exist):

```bash
php artisan test
vendor/bin/pint --test
# Developers may use: vendor/bin/pint
```

## 11. Security, Arabic Localization, Logging & Audit

- Each system operator must have a **personal user account**; shared reception/cashier logins are forbidden.
- Enforce authentication and permission checks at the backend. Sensitive read endpoints and exports require authorization as much as writes.
- No unapproved `Gate::before` role bypass or per-user role assignment rule is introduced merely by this code standard; design those details in Permissions Standards and Identity features.
- Identity user account and Employee business record remain separate with optional association.
- Use Laravel password hashing, validated inputs, safe query binding and CSRF protection **as appropriate to the authentication transport later selected**; rate-limit login and sensitive endpoints.
- API messages and user-facing fixed labels are **Arabic** using Laravel translation keys. Technical permission names, database keys and enum identifiers remain English and stable.
- Keep sensitive data out of Application Logs, Audit Logs and error responses: passwords, cookies, tokens, private child/guardian details, staff salary data, full payment credentials, stack traces and SQL dumps.
- Application Logs record unexpected operational faults; **selective centralized Audit Logs** record important business-sensitive changes only (actor, timestamp, reason where required, relevant before/after values). Neither replaces the Financial Movements ledger or timer-segment history.
- Audit changes linked to transactional business writes **as part of a coherent successful operation**, with no orphan audit rows after rollback.
- Production deployment must protect `.env`, restrict web root to Laravel `public`, and retain host-managed daily backups with verified restoration. The cPanel deployment details belong to Backend Architecture.

## 12. Avoid Overengineering

**Do not add by default:**

- Repository, Interface, DTO, separate read service, or Query Class **per CRUD endpoint**.
- Generic BaseController/BaseAction/BaseService/Manager hierarchies or compulsory layered architecture directories.
- A dedicated module for Selects, dashboards, notifications, or a single configuration table.
- Microservices, internal HTTP between modules, multiple databases, tenancy or branches.
- State-machine engines, general-purpose event sourcing, CQRS/outbox frameworks, or full double-entry accounting.
- Redis caching, queues, queued Jobs/listeners/notifications, Horizon, cron scheduling, or background workers.
- Payment gateway integrations, WebSockets, live push infrastructure or external report workers without an approved feature.
- New translation tables, multiple operating languages, or browser authentication mechanisms before their specs are approved.
- Unrelated refactors while implementing a small approved feature.

**Add abstractions only when** they materially improve clarity, eliminate demonstrated duplication, protect an actual module boundary, or make an important rule easier to test.

## 13. Feature Workflow & Definition of Done

**Implementation workflow:** follow the agreed **Spec Kit per-feature** sequence and the approved implementation roadmap: Foundation → core data/Identity → activities/café catalogue → Finance/POS → Sessions → subscriptions/attendance → Workforce/Payroll → Reports. A module may be delivered in several features and phases.

For a feature, read the project overview, backend architecture, **relevant** standards and approved feature `spec.md` / `plan.md` / `tasks.md` first. If the feature lacks an essential business rule (especially money, user permissions or subscription timing), stop and resolve that decision before coding.

**Definition of Done — applicable checks:**

- [ ] The feature's authorized behavior and acceptance criteria match the approved specification; no unrequested feature expansion.
- [ ] Mutations use **Actions**; Controllers remain thin; read queries are appropriately placed.
- [ ] Inputs use Form Requests; Policies/Gates check permissions; Actions enforce current-state business rules.
- [ ] Relevant module boundaries are respected; owning modules perform their writes.
- [ ] Financial and timer operations preserve history, use correct transactions/locks, and prevent duplicate effects.
- [ ] API output uses Resources and the **approved** shared response/error conventions; Arabic messages/labels use translation keys.
- [ ] Relevant PHPUnit Unit/Feature/Integration and MySQL-specific tests are added and **actually run**.
- [ ] Pint check passes; PR to `develop` passes required CI checks.
- [ ] Schema/seeders (if affected) are reversible/repeatable where relevant; no destructive changes to deployed history without a reviewed plan.
- [ ] No application queue, background Job, Redis, cron or scheduled business operation was introduced.
- [ ] Documentation and Spec Kit tasks are updated **only where the approved requirement or implementation status warrants it**.
- [ ] Any unavailable test, environment restriction or unresolved risk is reported accurately.
