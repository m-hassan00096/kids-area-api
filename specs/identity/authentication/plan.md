## 3. Approved database design (forward migrations; no destructive change)

All tables MySQL 8/InnoDB on the same primary connection as users. Time is UTC epoch units as explicitly documented. No extra lock/sentinel table, no Redis, no business hourly-session changes. The table named sessions here is Laravel authentication storage, not the future Sessions business module.

### 3.1 users: add credential generation

| Column | Type | Constraint / purpose |
|---|---|---|
| auth_version | BIGINT UNSIGNED | NOT NULL DEFAULT 1; monotonically increment on every successful password change/reset |

Existing users retain IDs, data, password hashes and roles; forward migration initializes auth_version only. Do not change username/email/phone collation or indexes. Hide auth_version from serialization and mass assignment, use explicit integer cast and checked increment. Do not allow reset/wrap or reuse of an old version. No index needed on auth_version alone because comparisons are per User ID. Do not use updated_at as a credential revocation version: ordinary profile/role metadata changes must not accidentally serve as a credential generation.

### 3.2 sessions: native database handler plus authoritative authentication metadata

| Column | Proposed MySQL definition | Index / purpose |
|---|---|---|
| id | VARCHAR(40) ASCII ascii_bin | PK; exact Laravel generated session ID; verify actual Store format |
| user_id | BIGINT UNSIGNED NULL | Native handler metadata/index; not an authorization grant |
| ip_address | VARCHAR(45) NULL | Native client-IP metadata |
| user_agent | TEXT NULL | Native request metadata |
| payload | LONGTEXT NOT NULL | Native Laravel session payload, encrypted with SESSION_ENCRYPT=true |
| last_activity | INT UNSIGNED NOT NULL | Native storage/GC epoch seconds; index |
| auth_user_id | BIGINT UNSIGNED NULL | Explicit authenticated owner; index (auth_user_id, id) or single owner index with PK coverage; verify query plan |
| auth_version | BIGINT UNSIGNED NULL | Version at the successful Login |
| auth_last_activity | BIGINT UNSIGNED NULL | Authoritative successful authenticated activity in epoch seconds; optional cleanup index only if justified |

Use native database session driver, not a custom session handler. Only the successful Login action may initialize the three auth_* metadata fields. Generic Laravel session writes must never create/restore those values: ordinary anonymous/late native inserts leave all three NULL, updates touch native payload/metadata only. Add a compatible MySQL CHECK that all three are NULL together or all are present (verify MySQL 8 support and actual DDL). Native user_id may be rewritten by the handler and is not an authoritative binding; the explicit auth_user_id is deliberately distinct. No token or persistent credential in session metadata. Laravel's encrypted payload may contain internal framework login state/CSRF material; never serialize it to an API response, log it, or invent a separate token.

Treat sessions as disposable authentication state, not historical business records: propose no FK from native session metadata, and no FK on auth_user_id, following native ephemeral-session practice; application checks require an existing current User and future authorized hard-delete action must retire that user's sessions in its transaction. Document this narrow FK exception for review rather than treating stale session rows as operational history. New sessions are independent per browser, no unique user_id constraint.

**Why extra metadata is needed:** native DatabaseSessionHandler (Laravel 12.73.0 inspected) saves payload, last_activity, and request/user metadata after downstream handling; it can insert a missing row, and routine saves update last_activity. Deleting rows alone or relying on native last_activity alone cannot prove password-change/logout revocation or that anonymous/failed traffic does not refresh authentication. auth_version plus explicit owner/activity binding prevents a stale payload from becoming authenticated even if an old request writes after deletion. No custom session engine, no additional auth grant table. Actual resolved handler behavior and atomic save path must be tested.

### 3.3 identity_login_throttles: minimal atomic two-scope limiter

Use one new Identity-owned transient table; it stores failure counters, not a lock/sentinel for RBAC. Native RateLimiter's separate cache tooManyAttempts/hit operations are not sufficient evidence of a race-free two-key rolling window. A DB row per scope/key with current row locks permits one atomic admission-and-result decision without Redis, file-lock dependence or cache-lock table.

| Column | Proposed type | Rule |
|---|---|---|
| scope | TINYINT UNSIGNED | 1 = username, 2 = IP (internal stable codes) |
| key_digest | CHAR(64) ASCII ascii_bin | HMAC-SHA256 hex of domain-separated exact username or canonical binary IP, with server key |
| failure_times | JSON NOT NULL | Bounded sorted list of UTC epoch milliseconds (at most 5/30 entries) |
| blocked_until_ms | BIGINT UNSIGNED NULL | End of the current temporary block |
| expires_at_ms | BIGINT UNSIGNED NOT NULL | Indexed logical cleanup deadline |

Composite primary key (scope,key_digest); index expires_at_ms for bounded batch cleanup. No users FK (unknown usernames are counted too), no raw username/IP, passwords, cookie IDs, request body or audit log in this table. Use dedicated key derivation/domain separation from APP_KEY, not a literal secret; normalize IPv4/IPv6 canonical address bytes, never lower/trim the username. Secret/key rotation is a separate operational decision; invalidate relevant existing auth/counters as required, do not log keys. Validate maximum entry count and expected data types; malformed state fails closed with safe operational error, not bypass. TTL makes retained row count proportional to traffic within a short retention window; absolute memory/cardinality under arbitrarily distributed abuse is not guaranteed. Review capacity and hosting perimeter controls before live rollout.

- GET /api/v1/auth/me: exact approved Resource, no top-level User ID.
- PUT /api/v1/profile/password: own password only, 200 Arabic message/data [], all affected sessions revoked.

Valid CORS preflight is handled before authentication, never counts as activity or creates a session; reject unapproved credentialed origins. Protect against spoofed Host/forwarded IP via explicit trusted hosts/proxies, not trust-all or wildcard credentialed CORS. Verify effective middleware priority for both api and native web handshake; do not add duplicate StartSession or CSRF middleware. Existing test-only probe and /up retain intended purpose. No unauthenticated real business API in this feature.

Pipeline for application endpoints: server request ID / safe global handling -> trusted first-party origin / reject token auth -> Sanctum cookie decryption + session start + CSRF -> guest Login or auth:sanctum -> authoritative StaffSession + fresh IdentityAccess -> route/Action/Resource -> qualifying authenticated activity update -> native session/cookie save. Explicitly prevent Bearer fallback before auth:sanctum (reject unexpected Authorization credentials, and use the resolved Sanctum token-retrieval callback to return no token if supported). Verify no missing personal_access_tokens queries or hidden token path. Protected authentication must originate from the web session, not merely an injected guard user.

Sanctum 4.5.0 native AuthenticateSession can compare stored password-hash fingerprints before our boundary. Propose configuring that optional Sanctum middleware off in favor of the stronger explicit auth_version/session-owner/activity checks on **every** protected application route; verify resolved behavior and coverage so there is no weaker parallel protected path. Keep native CSRF, cookie encryption, session handling and auth:sanctum. Do not disable security middleware globally. Treat the native password-hash fingerprint as internal framework payload only, not a second authority. A password rehash must not silently act as password change; use explicit Hash::check and web login, no automatic rehash/write during Login in F02 (all existing hashes already use Feature 01 Argon2id). Any later rehash policy requires reviewed semantics.

Cookie/config proposal: database driver, lifetime 720, payload encryption on, HttpOnly session cookie, Secure in deployment, SameSite=Lax (Sanctum stateful middleware itself sets Lax/HttpOnly in inspected tag), explicit domain/path, credentials-aware CORS for api/* and sanctum/csrf-cookie, HTTPS for real hosting, no wildcard domain/origin or remember-me cookie. Local test config may use explicitly controlled HTTP transport, never loosen deployed defaults. Public /api/* JSON errors regardless Accept; no login redirect. CSRF failure 419 before credential effects; missing/expired session 401 when CSRF valid. Browser flow: GET csrf-cookie with credentials -> send decoded XSRF cookie header on write -> Login -> Me; after logout/password change/401 or 419 obtain fresh handshake as applicable and reauthenticate.

## 5. Login and atomic rate-limit algorithm

### 5.1 Admission and failure counting

Use the approved exact username (case-sensitive ASCII, no trimming) and trusted client IP. Form Request rejects malformed fields with 422 before credential verification; invalid CSRF 419, non-stateful access 403. Do not let TrimStrings or ConvertEmptyStringsToNull alter usernames or passwords/currentPassword/passwordConfirmation; exclude these fields or the narrowly scoped Auth request path, verify Laravel 12 normalization behavior. Validate strings explicitly, including exact username regex and nonempty submitted password; no composition rule or trimming of spaces in actual passwords. New password requires >=8 characters and exact confirmation, including long passwords (Argon2id). Use standard request-size protection, no silent password truncation or new password complexity rule. Reject unsupported target/remember/token fields rather than allow clients to select another identity. Already authenticated eligible browser Login returns 409; stale auth context retired and must reauthenticate.

Serialize one admission/result within an outer transaction:
1. Resolve canonical IP and HMAC digests. Atomically insert-or-find the IP throttle row with no overwrite then acquire its exclusive lock; if blocked, return a denial outcome before allocating/locking a username row or hashing. Otherwise insert-or-find and lock the exact username row. Every attempt uses fixed order IP then username, no contrary order. Verify duplicate handling targets the exact composite key; never ignore arbitrary SQL errors.
2. Read current state after locks, using a coherent UTC millisecond clock. Purge failure timestamps at/before now minus 60,000 ms (rolling interval (now-60s, now]); when block expired reset that scope's failure state. If either block is active return 429 without hash work, with integer Retry-After = ceil(max(active expiry - now)/1000) (at least 1). A blocked attempt does not extend block or add failure. If both blocked and IP is checked first, obtain username expiry only if needed using the same ordered protocol, without creating a new username row for an IP-blocked request; return the longest applicable existing block expiry. Do not expose scope/counter/account existence.
3. When admitted, perform at most one actual credential hash verification (or equivalent dummy verification for a missing/unsupported account) and final eligibility validation as below. Locks deliberately cover check through credential outcome so simultaneous failures cannot exceed the admitted threshold. On failure, sample current time again, prune both rolling windows and append the failure to both scopes; at count 5 username or 30 IP set its block until failure instant + 60,000 ms. Threshold-triggering failure returns ordinary identical 401. All unknown identifiers and unusable accounts with valid-form credentials count. Successful Login clears only the username's failure state; IP history remains. Update expiration from last failure/window or block end; commit outcomes **before** mapping to safe 401/429/200. Throwing a 401 inside the transaction would roll back the counter, so return a typed outcome and render/throw after commit. No permanent account lock.
4. Cleanup expired records opportunistically, using small indexed batches (proposed max 100 per eligible periodic request; bounded frequency, not on every request; run outside auth transaction, recheck expires_at_ms at delete time, no reverse two-key locks). Expired data is logically ignored even if physical cleanup is delayed. No cron/worker or automatic cleanup of business data. No raw key in logs. Validate TTL/cleanup race on MySQL.

Trade-off: exact atomic counting requires holding two *per-key* rows during expensive Argon2id verification; it is not a global login lock, but shared-office IPs serialize login attempts. Limit waiting (proposed up to 5 seconds per contested operation, verify session innodb_lock_wait_timeout restoration; total request deadline measured); fail closed with safe 503 on verified contention/unavailable throttle store, no uncounted credential checking or incorrect 429. Do not extend lock via blocked requests. Hash outside the global Identity mutex; benchmark realistic concurrent staff logins and hostile failure bursts under approved CI/development. If the lock duration or capacity is unacceptable, propose a reviewed alternative (e.g. reservation scheme) rather than weakening thresholds. No arbitrary retry after an ambiguous commit; retry only demonstrably rolled-back admission before side effects, otherwise return safe failure.

### 5.2 Credential verification and successful Login transaction

- Query canonical User by validated exact username using the existing ascii_bin unique index; assert exact string equality on returned identifier. Do not query email/phone or use LOWER. Verify with Laravel Argon2id Hash::check. For unknown account use a synthetic non-account Argon2id dummy hash matched to current work factors, generated/validated in controlled config/development, not per request; no known real credential or sensitive secret stored. Wrong hash/account ineligible indistinguishable in safe public response and broadly equivalent hash work; no claim of mathematically constant network time. Do not log credentials or raw authentication events. A malformed stored hash is a safe denial/operational diagnostic, not a plaintext fallback.
- Do expensive Hash::check before acquiring global manager lock (while throttle locks are held). Read initial password hash/auth_version and eligibility from primary; after a correct password, acquire existing IdentityMutex (manager row) in the same outer transaction, then existing ordered current role/user/pivot locks via the compatible IdentityAccess boundary (currentHasAll([], userId) is a verified existing method signature; confirm eligible empty-required behavior and optimize only if needed). Re-read target User hash/version/username and actual eligible state under lock; compare to validated snapshot. If changed, deny and count failure; never authenticate based on old hash. No role-name bypass. Hold the shared Identity mutex only for this final successful-candidate recheck and session establishment, not for unknown/bad passwords. All cooperating access-affecting writes retain Feature 01 lock order. Password change never acquires throttle rows, so no reverse path.
- Once authorized, use Auth::guard('web')->login($user, false) and ensure the old session ID is destroyed and new ID/CSRF are generated (inspected SessionGuard::updateSession calls regenerate(true); test actual installed behavior rather than duplicate regeneration). Do not log credentials via Auth::attempt events. Persist the newly regenerated encrypted native session using native store/handler on the same primary connection **inside the transaction** before setting authoritative metadata. Verify the row exists with the correct new ID and native payload, then initialize auth_user_id, auth_version and auth_last_activity explicitly; exactly one row updated. Never promote a client-supplied or existing pre-login ID. Verify native write/exception behavior, because handler write can attempt fallback update on insert failure. All writes and throttle success outcome commit together; native downstream response save may update payload/last_activity but must never initialize auth_* metadata. Verify no double-save side effect relevant to API flash/CSRF state, and no success on failed persistence.
- If an exception/rollback occurs after native guard/session memory changed, clear in-memory auth state, invalidate/rotate the attempted session safely after rollback and do not let StartSession flush an authenticated-looking usable row; the authoritative marker is absent, so fail closed even on ambiguous late payload save. On ambiguous commit, report safe failure, attempt retirement of candidate session when connection is usable, never auto-retry login mutation with old verification. No cookie/token/password in response body. Successful 200 is returned only after required DB commit and framework response handling.

## 6. Session admission, activity, Logout and password change

### 6.1 Ordinary protected request

Check auth:sanctum and actual web-guard session (no token/actingAs shortcut in runtime). Query current primary database session auth_* binding together with actual User auth_version; validate exact authenticated owner equals guard's canonical User, matching version, and auth_last_activity > request time minus 43,200 seconds. At equality/older, or missing marker/row/user/version mismatch, reject 401 and retire current local/session state; do not keep old auth alive. Native last_activity/cookie expiration is not the authority. Then check active User, exactly one active web Role and no direct grants, using fresh IdentityAccess; authenticated but currently ineligible => 403, retire the unusable session. Protect Me from stale role data with a fresh joined/projection read of actual role and permission pivots (dedup lexical names, no direct grants). The initial eligibility/version check and Me projection should use one coherent primary read or explicit fresh revalidation, not mixed stale loaded relations. A permission denial is 403; ordinary read path never takes the manager mutex. Later module writes must recheck authorization at their own mutation boundary.

Proposed activity implementation: store an admission timestamp for a valid request; after a successful authorized 2xx response (other than Login initialized explicitly, Logout/password change revoked, or anonymous handshake/preflight), conditionally update auth_last_activity on the same session ID/owner/version with a monotonic GREATEST(old, admitted_at). Require row still present and its prior authoritative idle time eligible at admission; do not insert on zero affected rows, extend from response completion, or resurrect after concurrent expiry/revocation. No refresh on failed requests (including failed auth/authorization/CSRF/validation), anonymous CSRF handshake or simply holding a tab open. A concurrent expiry/revocation that already retired a row wins. This is the proposed precise activity rule for review; tests at 719:59, 720:00, later successful requests and overlapping failures/long requests must demonstrate approved idle behavior. Native session lifetime still 720; physical GC may happen later. Use native indexed last_activity cleanup lottery (proposed existing 2/100) and, if necessary, bounded opportunistic deletion of expired authenticated markers; logical expiry never depends on GC. Do not let handshake/native save revive expired authentication. Document session expiry under concurrent request ordering and measure ordinary request query count.

### 6.2 Logout current session only

Take authoritative current-session row lock/conditional delete (same primary; no need for global manager mutex). Recheck ID, owner/version and idle at authorization, delete/retire only that session; verify required persistence and commit. Clear native web guard (current device only, no remember token), invalidate/rotate native session and regenerate CSRF using framework API. Any late native save of old ID has no auth_* marker and cannot authenticate. No password/other-session changes. If persistence fails do not report successful logout; local browser context may be cleared for safety, but never claim old server session revoked without evidence. Confirm native cookie response, another device valid and repeated request 401/419. Ineligible authenticated request returns 403 and retires its old session; expired/missing 401 (or 419 when CSRF mismatches). No global session kill on ordinary Logout.

### 6.3 Password change and reusable revocation

Validate currentPassword, password, passwordConfirmation exactly (no target ID). Authenticated eligible staff only, ID 1 included. Initial Hash::check against actual snapshot and new Argon2id hash preparation outside locks; incorrect current password 422 with field error and no credential/session writes. No requirement to differ from old password beyond approved rules; a successful change always rotates generation.

Own one outer MySQL transaction: existing manager row mutex -> role/user current locks in Feature 01 order -> initiating session row check (active binding, version and idle) -> explicit current User row hash/version comparison -> write new hash and increment auth_version (verify affected row) -> delete all sessions with auth_user_id = target, including initiating session (indexed lookup, deterministic order when explicit row locking needed). For eligible session check before mutation use current reads, never stale REPEATABLE READ snapshot. A concurrent change that invalidated the initiating session returns 401; if current password incorrect without revoked session, 422. If a DB write/required revocation fails, rollback both password and session retirement; no cookie/auth invalidation before known successful commit unless needed to fail closed on an ambiguous outcome. When committed, clear native initiating guard/session and rotate CSRF; require re-login. Other User sessions untouched. Old payloads cannot authenticate because authoritative binding missing or generation obsolete. No attempt to cancel already authorized in-flight operations retroactively; sensitive future writes check current authority at mutation time.

Expose only a focused internal credential-revocation operation callable within the same outer transaction for Feature 03 authorized administrative reset, target determined server-side. Its caller must hold appropriate manager/role/user locks and perform all target authorization/invariants; no independent nested transaction/unguarded direct password update. Future deletion must retire sessions, not treat them as important history. No admin reset API or new founder permission here.

**Lock order and failure boundaries:** Login IP throttle -> username throttle -> manager mutex -> ordered role/user/pivots -> affected session rows. Profile/other future Identity credential mutations start manager -> ordered role/user/pivots -> session rows; never acquire limiter after manager. Ordinary session read/touch/logout/cleanup only operates on session rows, no later manager/user locks in same transaction; if a fresh user read is needed, perform it before session-row lock or as non-locking current-primary admission query, not reverse acquisition. Avoid expensive hashing, network/filesystem I/O and user interaction under manager lock. Bound locks/timeouts and verify exact query/transaction behavior with independent connections. Deadlock or failed mutation aborts the entire operation; no blind retry after session ID allocation/credential commit ambiguity. All post-commit cleanup is idempotent and cannot grant authentication.
