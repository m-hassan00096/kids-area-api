## 6. Transaction, actor and lock ordering

Reuse native Spatie Role create/save/syncPermissions/delete and existing single-role assignment Actions. Keep one outer transaction, one attempt (no blind retry), existing permanent manager mutex. Do not simply call IdentityAccessMutation::execute (legacy actor ID without admitted session check) or executeUsers/CurrentStaffMutation::lock unchanged (requires users_target and Users-specific outcome/file semantics). Extract a minimal shared current-authority/binding primitive or introduce a Roles-specific boundary using reviewed shared primitives; preserve F01/02/03 public behavior and outcome handling. Do not add a second lock table. Existing broad IdentityAccess::currentHasAll locks roles/users/memberships/direct grants/catalogue/grants in stable order; inspect actual lock order and preserve compatibility with Login, Profile, Users and Seeder. Plan:

1. Validate shape and obtain admitted actor/target ID outside transaction; no mutation before lock.
2. Acquire manager mutex first on same connection; bounded 5s per conflicting lock, not end-to-end SLA. Lock access rows in existing stable order (roles then Users then ordered membership/direct/permission/grant rows); use current reads. Re-evaluate actor's capability, current eligibility, original admitted auth_user_id/version and current initiating session. Acquire/re-read target/affected access rows before locking session rows, preserve ordering and prevent reintroducing role locks after session lock unless already held. Unauthorized target lookup/mutation never precedes capability. Retire only genuinely invalid browser after rollback; missing permission alone must not delete valid session.
3. Re-read exact target and named catalogue under lock; verify database uniqueness and permanent role protections. For create, use authorized name and web guard, active default, resolve exact approved Permission models and sync grants. For PUT, keep ID and guard, rename custom name, replace grant set atomically using native package methods; no direct user permissions. For DELETE, require no membership (all User states, fail closed anomalies) checked under same mutex/current locked pivot query; delete via native model so role grant pivots cascade only after check. An authorized assignment concurrent with deletion shares mutex and revalidates target: whichever wins, other observes current state, no lost role assignment or implicit cascade. Unknown/wrong-guard definition anomalies fail safely rather than normalize away.
4. On true->false custom disable, acquire target users and relevant membership locks in stable ID order while under mutex, ensure all associated Users included even inactive; preflight every auth_version within safe integer range, increment exactly once and remove all authoritative sessions using existing owner index and SensitiveQueryScope. Prefer existing CredentialRevocation semantics in ordered bounded batches (no per-account transaction/commit); evaluate set-based conditional updates/deletes if actual performance warrants and same exact affected-row/overflow/failure safeguards can be demonstrated. Do not lock unbounded unrelated session rows or hash/change passwords. Repeat inactive, enable, rename and permission-only edits do not revoke or increment. Actor on affected role can disable own custom role only if authorized and another viable admin remains; mark self-revoked only after commit, clear browser via StaffSession::clearRevokedBrowser, suppress touch. Stale native session write may leave anonymous row but old generation/authority cannot revive, even after re-enable. Login commit-first revoked by disable; disable-first Login fails or must establish a new valid session after reactivation; never reuse prior authority. Already-admitted ordinary reads can finish; new protected requests and current mutation checks reflect committed grants.
5. Re-evaluate permanent role existence/name/ID/active and at least one eligible User with exact six essential permissions before commit. Roll back all role fields, pivots, User generations and session deletion if invariant fails; no partial cleanup. Concurrent Role and User changes share same mutex; do not change protected founding User rules or make role name the authority.
6. Use one acknowledged commit. Distinguish known rollback, known committed and uncertain acknowledgement; restore prior per-connection lock timeout only on healthy known connection, disconnect otherwise. No automatic replay or claim rollback on lost acknowledgement. Spatie permission cache invalidation after known commit and rollback, not solely package in-transaction eviction; native APIs may evict before commit so test cross-process repopulation and authoritative primary request path. Post-commit cache/session cleanup failure report safe correlated diagnostic and preserve known committed outcome; if failure prevents safe response, distinguish failure response from actual rollback and reconcile authoritative state before resubmission. Keep existing permission authority fresh rather than introduce Redis/TTL dependence. No Audit event or fake audit until deferred feature.
